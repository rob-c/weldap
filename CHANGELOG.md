# Changelog

All notable changes to WELDAP are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and the project aims to follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **Build-time tile picture**: `WELDAP_TILE_IMAGE` (`vm/build-in-vm.sh`) or `build.ps1 -TileImage` compiles any
  square PNG/JPEG/GIF/BMP into the credential provider as its logon-tile image, checked and normalised to a
  192×192 24-bit bitmap at build time. See `docs/CONFIGURATION.md` §3.

### Changed
- The default tile picture is WELDAP's own collider event display (`art/tile.bmp`, generated by
  `art/make-tile.py`), replacing the Microsoft sample's "Controls" bitmap.
- Pipe request byte 1 is now a flags byte (bit0 unlock, bit1 adoption consent; any other bit is malformed). After
  an `adopt` reply the tile shows the warning and a **Continue** box; a resubmit with it ticked consents.
- One time budget, outermost first: tile 15 s > service 14 s per pipe client > one server round trip 9 s
  (connect 3 s, TLS handshake, request, reply).
- Once running, any fault exits with code 1 and the SCM restarts the service 5 s later (the MSI and
  `install-dev.ps1` set the failure flag); a refusal at start (config, ACL, integrity) logs a critical event and
  stays stopped. If another process holds the pipe name, the service retries with backoff.
- `ServerKey` (65-byte P-256 point) and `ServerKeyId` (1–32 of `[a-z0-9-]`) are validated at service start;
  the setting ranges are clamped in Core. The service's own Information events now reach the event log.
- Built-in accounts are recognised by SID (RIDs 500/501/503/504), so renamed or localised ones are protected;
  `weldapadm` shows them as `built-in`. Account names are handled lower case.
- Every online sign-in re-applies the stored local password, so an account reset by hand converges back. A
  Windows logon failure now reads "This PC's account is out of step with WELDAP" instead of blaming the password.
- Reconciliation is two-phase (asks the server without the account lock, applies under it against a fresh account
  list). Idle-disable is measured against the most recent logon on the device too, so a clock stepped forward or
  a device left off does not idle-disable everyone; accounts that never logged on are never idle-disabled.
- `DemotionSkipped` (event 1214); `WouldDisable`, `DisableSkipped` and `DemotionSkipped` are Warnings.
- `weldapadm`: `adopt` refuses unusable, excluded, protected and already managed names; `disable` and
  `set-admin … off` refuse the last enabled local admin; `force-local` takes only `<name>` or `<name> --off`; any
  failure is a message and exit code 2.
- MSI: numbers and lists are written as REG_SZ (the service also reads REG_DWORD / REG_MULTI_SZ); the provider
  DLL is installed as `WeldapCredentialProvider-<first 12 hex of its SHA-256>.dll`, so an upgrade at the logon
  screen needs no reboot; Programs and Features offers Repair and Uninstall, not Change. `build-msi.ps1` takes
  `-ProductVersion` (or `$env:WELDAP_VERSION`).
- The rate limiter lifts a block if the clock steps backwards rather than stretching it.
- A server-side throttle now says "Too many sign-in attempts. Wait a few minutes and try again." instead of "Too
  many failed attempts…": the server also throttles a whole device (30 requests a minute), which refuses users who
  have not failed at all.

### Fixed
- An abandoned pipe client could stop the service (exit code 0, so never restarted), taking all WELDAP sign-in,
  offline included, down with it; the pipe loop also no longer waits unbounded (`WaitForPipeDrain`).
- The TLS handshake to the server had no timeout.
- Adoption was impossible: the tile rejected the `adopt` reply as a protocol error.
- The consent box could be ticked while hidden (sending consent with no warning shown), and setting the same name
  again withdrew it (adoption could loop); consent is now bound to the name the warning was shown for.
- Concurrent sign-ins (several sessions) queued behind one another's server round trip on a single pipe instance
  held under the account lock, so a later one could time out after the service had already acted on it. The
  service now serves 8 pipe instances and holds the account lock only for account changes, deciding against the
  account as it is after the server answered.
- The last-admin guard was undone by a demotion in the same pass; the last enabled local admin is now never
  disabled or demoted, on every path.
- Armed lockdown never disabled anything (the Windows layer refused every unmanaged account).
- Adoption reused a stale stored password from an earlier account of the same name.
- Mixed-case local accounts (`Alice`) were not matched to their directory user (`alice`) by adoption,
  reconciliation and lockdown.
- Offline sign-in was possible for a pre-existing unmanaged account (FR-15).
- Force-local was ignored for an account that was also managed: the tile signed it in.
- A corrupt stored local password stopped the service; it is now treated as missing.
- Disabling a removed user and forgetting its verifier no longer depend on each other.
- A lone-surrogate escape in a server reply threw instead of being treated as malformed.
- A negative stored offline-failure count is treated as locked (it granted extra offline tries).
- A full or broken event log could leave the service neither serving nor stopped: a log call that threw inside its
  fault handling hung the host with exit code 0. No log call can throw now, and the exit code is set first.
- Under armed lockdown the last-admin guard could keep a removed WELDAP user (unusable) and disable the working
  local admin; managed accounts are now reconciled first, so the guard keeps a usable admin.
- One connect timeout covered every address of the server's name, tried in turn, so a black-holed first address (an
  IPv6 black hole, a dead round-robin node) hid a working second one; each address now gets its own.
- A policy value present but unreadable (wrong type, "off") silently fell back to its default, failing open; it now
  stops the service with a clear event.
- An interrupted uninstall (cancelled, power lost) could roll WELDAP back with its state already deleted; the purge
  now runs only after the uninstall has succeeded, and only when the product is really installed: `REINSTALL=ALL`
  given to a different build made Windows Installer treat the session as a removal (it sets `REMOVE=ALL` itself),
  which ran the purge under the still-installed product. That session is now refused up front.
- A rebuilt MSI installed side by side as a second "WELDAP" product; any rebuild, same version included, now
  upgrades in place, as one transaction.
- An upgrade wiped per-device state (local passwords, offline verifiers, hand-set policies), and a repair blanked
  the settings; both are now kept, every setting remembered from the registry. Upgrading **from 0.1.0** still
  loses that state once (0.1.0's own uninstall deletes the key): users sign in online once and hand-set policies
  must be set again.
- The x64 MSI installed silently on ARM64 Windows, where LogonUI cannot load it; it now refuses.
- Dev builds all carried the same MSI version, so a stale MSI silently replaced a newer build; `build-msi.ps1` now
  stamps `<major>.<minor>.<days since 2026-01-01>` and Windows Installer refuses an older build.
- The documented repair (`msiexec /fa…`) could reboot the PC unannounced: in the `/f` form `/norestart` is not
  applied, and mode `a` overwrites `WeldapService.exe` milliseconds after the service stops, while the process is
  still exiting, so the file was replaced at a reboot. The guide now gives
  `msiexec /i <installed MSI> REINSTALL=ALL REINSTALLMODE=omus /qn /norestart`, verified on a device with no reboot.
- The service's own events (why it refused to start, the integrity status) had generated 32-bit ids that Event
  Viewer could not describe, so the reason showed as an unreadable event; they now have fixed ids 1500–1512.

### Security
- Device registration could be hijacked by a standard user who pre-created the registration folder (under
  ProgramData) with an ACL of their own: `icacls /grant` kept their entries, so they could swap the CSR for one of
  their keys. `register-device.ps1` now refuses links, takes ownership and sets a fresh protected ACL on the folder
  and its parent, empties it, and removes a certificate it could not bind to the device's key.
- No MSI property is `Secure` any more, so a standard user can no longer pass `SERVERHOST`/`SERVERKEY`/… into an
  elevated repair and redirect every password; the install folder's id is private (a custom folder could have a
  user-writable ACL).
- A `Secret` key deleted while the service ran was re-created by the next sign-in with its parent's ACL, readable
  by Users; it is now always re-created SYSTEM-only and checked first.
- A pre-existing local administrator could be adopted by a non-admin directory user, whom the last-admin guard then
  kept an administrator for good; adoption now refuses a local admin the directory does not make one, and any
  disabled pre-existing account.
- Lower-casing account names used Unicode case folding, so a lookalike name (a Kelvin sign for "K") passed as a
  directory user's and escaped lockdown; only A-Z are folded now.
- The audit sink never throws, so a full or broken event log cannot fail a sign-in or leave a local password
  un-zeroed.
- A stored local password that is not exactly what the generator makes is never handed to LogonUI.
- The provider DLL no longer links `credui.lib`/`gdi32.lib`; `credui.dll` left the import allow-list.

### Supply chain & tooling
- **Release pipeline** (`.github/workflows/release.yml`): on a version tag, builds and publishes the server
  container to GHCR, mints a signed build-provenance attestation for the image, generates SBOMs (SPDX and
  CycloneDX) for the server image and the client, and attaches them to the GitHub release. Uses only
  first-party actions plus pinned CLIs/containers, adding no new marketplace-action surface.
- `docs/RELEASING.md`: the release procedure, provenance/SBOM verification, and the manual Windows MSI step.
- `tests/quality.sh installer` (in `--fast` and CI): the MSI source is well-formed XML and keeps each installer
  safety fix above (no Secure property, private install folder id, commit-phase purge for a real uninstall only,
  foreign `REINSTALL` refused, ARM64 check), on the host in a second rather than in the build VM.

## [0.1.0] - 2026-10-31

First public release — a pGina-style Windows logon that authenticates a user against an LDAP directory
without the password ever living on the device.

### Added
- **Credential provider** (C++, in LogonUI): seals the typed password with HPKE (RFC 9180 base mode,
  DHKEM(P-256, HKDF-SHA256) / HKDF-SHA256 / AES-256-GCM) and computes a machine- and user-bound PBKDF2
  offline verifier.
- **Windows service** (C#/.NET 10): a SYSTEM-only named-pipe server that talks to the WELDAP server over
  mutual TLS (per-device certificate; server trusted by public-key pin) and creates or updates the local
  account, logging the user on with a random local password.
- **WELDAP server** (Rust, AlmaLinux 9 container): the only LDAP client of the directory; opens sealed
  passwords in locked memory, binds as the user, and returns two flags — `user` and `admin`.
- **Offline sign-in** against the PBKDF2 verifier, with a configurable maximum age and a failure lockout.
- **Reconciliation**: the device asks the server only about its own managed accounts; upstream removals
  disable the local account and clear its verifier.

### Security & hardening
- 100% line+branch coverage of the platform-neutral client logic; 100% line+region coverage of the server.
- Device trust by mutual TLS with a mandatory CRL (fails closed); server trust by SHA-256 public-key pin;
  startup anti-tamper check that the registered provider DLL matches the MSI-pinned hash.
- Stripped binaries, no shipped debug symbols, a shell-less runtime image, CFG/CET/ASLR/DEP and `/analyze`
  on the provider, every Linux capability dropped, `mlockall`, `panic = abort`.
- The password never reaches a log at any level (enforced by a lint); secrets are zeroed and the server
  holds them only in locked memory.
- Hostile-network resilience: bounded connect/handshake/request deadlines and TCP keepalive on both ends,
  so a black-holing or truncating middlebox becomes a clean offline fall-back or a dropped connection.

### Supply chain & tooling
- GitHub Actions CI running the full host gate set (lint, client, server, cargo-deny) on every push and PR.
- `cargo-deny` (advisories, licences, bans, sources); Docker base images pinned by digest; NuGet lock files
  restored in locked mode under CI; Dependabot across Cargo, NuGet, Actions and Docker.
- `tests/quality.sh` gate runner, a cross-language protocol-constant consistency check, a PE import
  allow-list for the provider, the no-secret-in-logs lint, and per-component code-size budgets.
- `docs/ARCHITECTURE.md` maintainer guide; a `Makefile` and a dev container for the local loop.
